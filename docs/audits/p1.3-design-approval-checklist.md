## 1. Backward-compatible SESSION and POS bill schemas — PASS

- **Evidence:** `README.md` §C.3 §3.1 field table and **"Backward compatibility rules (no backfill)"** (legacy docs treat missing `origin` as `SESSION`, missing `audience` as `CUSTOMER`, missing `billedTotalPaise` as `totalPaise`, missing `lines` as derived; no field renamed/removed; `userId`/`sessionId` loosened, never tightened). POS schema in §3.2 (`orders: []`, `sessionId:null`, `userId:null`, `lines:[...]`). Legacy read normalisation in §3.3(f) and §6.
- **Code cross-check:** current `Bill` fields `server/models/Bill.js:71-88`; existing indexes `:90,94,96`. The design adds fields/indexes without renaming any current key.
- **Correction:** none.

## 2. Immutable audience, snapshots, quantities, integer-paise money — PASS

- **Evidence:** `README.md` §C.3 §4 invariants 1–2 ("Existing bill snapshots never change… New `lines`/`audience` are write-once") and §3.1 (`lines:[billLineSchema]`, `audience`). Integer-paise storage discipline stated in §2.2 (`billingUtils.js:70-85`) and reused by `billLineSchema.pricePaise`/`linePaise` (`Bill.js:48-58`).
- **Code cross-check:** the only post-create mutations are `payments`/`status`/`amountPaid`/`balanceDue` (`Bill.js:108-435`); no endpoint writes pricing fields. So immutability is currently enforced **by code paths only** (no DB-level guard).
- **Recommended (non-blocking) correction:** add one sentence to §C.3 §3.1/§4.2 stating immutability is enforced by the absence of any write path (and optionally `immutable: true` on `audience`/`lines`), plus a regression test that pay/void/resume never alter `audience`/`lines`/`totalPaise`. This does not block approval.

## 7. Idempotent retries + same key / different hash rejection — PASS

- **Code cross-check:** no current idempotency handling on bill creation (verified absent, §2.3).
- **Correction:** none.

## 8. Payment/reversal/void/resume recovery for both SESSION and POS — PASS

- **Code cross-check:** `Bill.js:313,357,423`.
- **Correction:** none.

## 9. Separate finalized-bill analytics and legacy order metrics — GAP

- **Covered:** `README.md` §C.3 §4 invariants 4–5 (new bill analytics aggregate `Bill.totalPaise` of finalized bills; legacy `/api/orders/analytics` left byte-for-byte unchanged), §2.7 (legacy order analytics analysis), §9 file list (`getBillAnalytics` in `billingController.js`; `GET /analytics` in `billingRoutes.js`).
- **Gap:** §C.3 §3 is titled **"Proposed schema and API contracts"**, but the new analytics endpoint has **no request/response contract**. §3.3 provides contracts for generate/POS/retrieve/payments/void/DTO only; analytics appears solely as an endpoint name in §9. In addition, the definition of "finalized" is an unresolved **ASSUMPTION** (§4.5 / §8 Q2).
- **Required correction (documentation-only):** add a §3.3(g) analytics contract specifying `GET /api/billing/analytics` query parameters (e.g. `from`, `to`, `origin`, `audience`) and a response DTO, and state the finalized status set as a decision (proposal: revenue = `SETTLED`; `OPEN` shown as billed-but-unsettled; `VOIDING`/`VOID` excluded) subject to owner confirmation (Q2). No code change.
- **Code cross-check:** no `Bill.aggregate`/bill analytics exists today (§2.7).
